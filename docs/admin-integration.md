# 原后台与商城业务融合

`/admin`、`/admin.html` 和 `/?admin=1` 都使用原运营后台的深色侧栏、橙色界面和菜单顺序。所有入口继续校验管理员角色。新业务嵌入对应栏目，商品详情编辑器和完整 SKU 编辑器也使用同一个后台框架。

| 栏目 | 保留的功能 | 接入的业务 |
| --- | --- | --- |
| 欢迎页 | 原运营数据看板、提醒 | 商城交易概览 |
| 订单管理 | 人工订单录入、审核、交付记录 | 商城订单、支付后发货、原路退款 |
| 工单管理 | 原客服工单 | 顾客投诉、回复、退款和换货 |
| 车辆管理 | 车辆、车位、库存账号池 | 卡密导入、有效期、库存状态 |
| 代充值记录管理 | 原充值服务交付记录 | 钱包充值与退款流水 |
| 车票管理 | 原车票和交付凭证 | 商城订单交付 |
| SPU 配置 | 名称、分类、图片、主体资料 | 原详情页编辑器和订阅类型模板 |
| SKU 配置 | 原定价、供货数量、成本、标签及完整编辑器 | 自动发货、售后期限、自动换货次数 |
| 服务配置 | 首页文案、站点设置、自动交付和低库存提醒 | 全站自动交付开关控制商城订单；提醒阈值共用 |
| 其他原栏目 | 用户档案、供应审核、供应商、营销/IP 定价、线索、运营人员 | 保留入口、编辑和数据保存 |
| 支付与退款 | 新增统一入口 | Stripe、钱包支付记录、退款审批与对账 |

## 数据保存

- `go_products.commerce_product_id` 关联原商品与商城商品，原商品 ID 保留。两边编辑共同字段会同步；保修及换货规则由交易配置维护，供货数量不冒充可售卡密数量。
- 原后台提交基于加载时数据的字段差异，通过管理员专用 RPC 在事务中保存。删除只针对明确移除的 ID，不再先清空整张表；刷新后台只读取数据。
- 原商品删除会将商城商品下架，保留订单依赖的商品和交易记录。
- 原人工订单、客户档案、车辆账号和工单继续保存在原表中。原人工记录的“退款”操作记录线下处理结果；实际 Stripe 或钱包退款走商城交易接口。原运营人员档案不直接授予 Supabase 角色。
- 原账号池需核验后导入商城卡密模块。融合部署不会自动出售旧账号、生成付款或把人工记录当作已到账交易。
